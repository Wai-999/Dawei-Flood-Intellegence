# Private Drive recovery — prepared, not commissioned

October 4, 2026 UTC. The owner authorized the existing Google Drive as an encrypted backup destination and the narrowly scoped desktop backup client. The required policy agreement was personally accepted by the owner. The Drive API and OAuth app/client were prepared. Private credential replacement and actual owner consent are pending; no Drive token, folder, upload, quota verification or restore is claimed.

Request only `https://www.googleapis.com/auth/drive.file`, using a loopback desktop flow with PKCE and state validation. This scope covers app-created or explicitly selected files; SDK cloud consent is separate. Google recommends narrowly focused scopes and identifies `drive.file` as non-sensitive. Credentials, authorization codes and refresh tokens stay private and out of browser/tool output. [Official scope documentation](https://developers.google.com/workspace/drive/api/guides/api-specific-auth).

The prepared app is in External Testing. Google issues refresh tokens that expire after seven days for this configuration when Drive scopes are used. An initial successful grant therefore cannot establish durable unattended recovery. Record actual publishing status and token lifetime, and obtain any required owner authorization before changing them. Handle revocation/expiry by preserving backups and alerting, with bounded retries. [Official refresh-token rules](https://developers.google.com/identity/protocols/oauth2#expiration).

Current standard Drive API use has no additional charge, while quota excess can incur or is planned to incur charges. The current published thresholds include 1 TB of project egress per day and 400 million quota units per day; these are provider limits, not a project spending cap. Verify actual project-wide usage, owner storage headroom and current pricing before transfer. Bound requests, payload bytes, downloads and total retained storage conservatively; do not increase quota, purchase storage or infer headroom from a delayed zero bill. [Official limits and pricing](https://developers.google.com/workspace/drive/api/guides/limits).

## Evidence required before activation

1. Obtain the actual exact-scope owner grant and verify quota/privacy. Create a dedicated app-owned private folder and verify that no public or unintended sharing exists.
2. Encrypt a freshly inspected signed operational copy on the trusted host using the owner's public age recipient. Keep the private age identity exclusively in owner custody. Transfer only ciphertext to the approved destination.
3. Download that actual Drive object, verify its full hash, then perform a signed isolated restore on the owner computer into a new unique directory. Verify integrity, foreign keys, schema, source hashes, protected operational/owner row parity and invalidated restored sessions. Preserve every previous checkpoint.
4. Install credentials only in a root-controlled backup-specific path, inaccessible to app, Telegram and Sheets. Verify actual mount/permission isolation, bounded scheduling, retry limits, request/byte accounting, freshness and alert behavior before enabling unattended transport. No automatic remote-history deletion is authorized.

Drive can preserve files outside the Google Cloud trial's resource lifecycle, subject to actual access and storage checks. The same Google owner identity does not provide Google-account-loss independence. Retain separately custodied ciphertext, the private age identity and trusted actual-host signing escrow outside that account. Custody, retention, on-call/alert delivery and recovery traffic switching remain owner decisions. Existing owner-side signed restores are actual checkpoint recovery evidence, not a guarantee of continuing transport or RPO.

## Credential isolation preparation

[drive-config.py](../infra/drive-config.py) converts an actual, fresh, exact-scope desktop grant into a private rclone configuration only after a verified app-owned private folder exists. It requires matching replacement client credentials, exact requested/granted `drive.file` scope, a refresh token, unexpired access token and consent evidence no older than one day. Unexpected endpoints, broader scopes, malformed fields, unsafe permissions and symlinks are refused without printing credential values. This local conversion makes no provider request and does not enable a timer or mark recovery commissioned.

The production installer requires root and writes only `root/backup-secrets/drive.conf`, with directory mode 700 and file mode 600. It refuses replacement of any existing credential. That directory must remain outside all app/Telegram/Sheets bind mounts; verify actual isolation before using it. Never put a Drive grant into the existing shared `root/secrets` directory. Owner decryption identities remain off-host.

The existing encrypted upload/download command accepts an explicit `--rclone-config` only at that backup-only path. Its GCS default, signed-copy inspection, encryption-before-transfer, capacity guard, bounded retries and literal-download hash verification remain intact. The scheduler still uses the existing GCS configuration; no Drive credential or scheduled activation has been deployed. The [rclone Drive documentation](https://rclone.org/drive/#drive-file) describes app-created file scope and the fixed root-folder setting. Actual project/owner quota, folder permissions, token lifetime, request/byte bounds, upload/download, isolated restore and timer/isolation checks remain required before Drive activation.
